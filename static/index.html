Overview

This dashboard drives a VMware → Proxmox migration pipeline: you pick guests, enqueue jobs, and a worker (separate process) performs import, disk layout, reboots, and guest steps. It fits batch / VDI-style moves when combined with your own Horizon / Omnissa guest scripts in configuration. This project was created primarily for Windows 11 VDI migration, but can also be used for recent Windows Server guests.

Typical workflow

  1. Complete Settings (Proxmox required; VMware optional for extra columns).
  2. Open Guests, select VMs, then Migrate selected to enqueue jobs.
  3. Use Migrations to watch progress, open Details (timeline + logs), stop or bulk-cancel queued jobs.

Dashboard & operator features

  • Session UI — Password login; dashboard after credential verification gate.
  • Guests — Inventory from Proxmox ESXi-linked storage; optional vCenter merge (MoRef, UUID, power) when VMware is configured.
  • Migrate — Per-VM Proxmox VMID allocation, node, storage (dropdown + manual), RAM/CPU, optional QEMU CPU preset (nested/VBS), optional simulated import (clone template on PVE).
  • Migrations — Redis-backed states; list with progress bar; Details (timeline, error, log tail with auto-refresh, copy diagnostics); Logs modal; Stop; bulk cancel for PENDING; polling slows when the browser tab is hidden.
  • Settings — Load/save config.yaml sections with masked secrets; test Proxmox and VMware connections.
  • Services strip — GET /health: config + Redis + Proxmox (required); VMware (optional, warning not red).

API, worker, safety & deployment

  • Safety — Optional proxmox.safety envelope (VMID range, storage allowlist, scratch purge naming) enforced on enqueue/worker.
  • Worker pipeline — Import / simulated clone, SATA boot path, guest agent, SCSI swap; optional WinRM PowerShell (horizon.powershell_script) hook kept mainly as a placeholder for future guest automation.
  • REST — Authenticated /jobs, /vms, /migration-defaults, etc.; public /health and /version.
  • Deploy — Docker Compose stack documented (API + worker + optional Redis); nginx reverse-proxy notes.

Horizon / guest automation (today)

The WinRM/Horizon step is optional in this release and is commonly left as a placeholder script. When enabled, the worker runs your PowerShell over WinRM from horizon.powershell_script in config.yaml. There is no built-in Connection Server REST client yet (pool moves, re-register to manual pool, etc. are design notes under docs/).

Potential roadmap (ideas, not commitments)

  • Resume / retry — Operator-triggered resume when only the Horizon / WinRM stage failed (idempotent scripts).
  • Horizon Connection Server API — Optional integration for manual pool registration, entitlements, inventory sync.
  • Preflight / dry-run — Validate enqueue inputs without starting destructive work.
  • Job metadata — Pool / wave labels for reporting; richer audit trail.
  • Live logs — SSE or WebSocket if log volume grows; split cheap vs deep health checks.
  • Config validation — Stricter schema at startup; optional https_only cookies when always behind TLS.

Security considerations

  • Exposure — Prefer private network or VPN; put the UI behind TLS (e.g. nginx). This tool drives Proxmox and guest automation; treat it as admin-tier.
  • Secrets — config.yaml holds passwords and API tokens; restrict file permissions and backups. Redis holds job fields (including guest credentials used for WinRM); use ACLs, auth, and a dedicated DB index; protect Redis dumps.
  • Sessions — Single shared dashboard password; session cookie flags depend on app settings — see SessionMiddleware in code. Consider login rate limiting at nginx for internet-facing installs.
  • Public endpoints — GET /health and GET /version need no login; they can reveal coarse dependency status — restrict by network if that matters.
  • Infrastructure accounts — Use least privilege Proxmox tokens and VMware roles; keep proxmox.safety aligned with what those accounts may touch.
  • Guest scripts — horizon.powershell_script runs with supplied WinRM credentials; treat script changes like production code (review, no secrets in logs, idempotent where possible).

Where things run

  • This web app — FastAPI UI + API (browser or reverse proxy).
  • Worker — Consumes Redis queue; talks to Proxmox API and guests (WinRM).
  • Redis — Job state, logs, queue (see deployment docs for host vs container Redis).
