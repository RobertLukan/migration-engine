Overview

This dashboard drives a VMware → Proxmox migration pipeline: you pick guests, enqueue jobs, and a worker (separate process) performs import, firmware/devices, and guest-agent checks. It fits batch / VDI-style moves for Windows 11, Windows Server, and Linux guests.

Typical workflow

  1. Complete Settings (Proxmox required; VMware optional for extra columns).
  2. Open Guests, select VMs, then Migrate selected to enqueue jobs.
  3. Use Migrations to watch progress, open Details (timeline + logs), stop or bulk-cancel queued jobs.

Dashboard & operator features

  • Session UI — Password login; dashboard after credential verification gate.
  • Guests — Inventory from Proxmox ESXi-linked storage; optional vCenter merge (MoRef, UUID, power) when VMware is configured. PVE ESXi storages shows which linked-storage ids list each guest (parallel import-from across different ids when permitted). Size uses the listing's size field for the chosen disk.
  • Migrate — Per-VM Proxmox VMID allocation, node, storage, per-VM memory/cores (prefilled from PVE VMX import-metadata) and VLAN (operator-set), optional QEMU CPU preset, firmware mode (importer-resolved or per-VM override for UEFI/SeaBIOS, Windows/Linux, vTPM).
  • Migrations — Redis-backed states; list with progress bar; VMware / import queue (API host, import path, shared permit bucket for parallelism); Details (timeline, error, log tail with auto-refresh, copy diagnostics); Logs modal; Stop; bulk cancel for PENDING; polling slows when the browser tab is hidden.
  • Settings — Load/save config.yaml sections with masked secrets; test Proxmox and VMware connections.
  • Services strip — GET /health: config + Redis + Proxmox (required); VMware (optional, warning not red).

API, worker, safety & deployment

  • Safety — Optional proxmox.safety envelope (VMID range, storage allowlist, scratch purge naming) enforced on enqueue/worker.
  • Worker pipeline — ESXi/NFS import-from to scsi0, firmware devices (EFI / vTPM when applicable), then guest-agent reachability checks.
  • REST — Authenticated /jobs, /vms, /migration-defaults, etc.; public /health and /version.
  • Deploy — Docker Compose stack documented (API + worker + optional Redis); nginx reverse-proxy notes.

Import permits & parallelism

The worker’s main throttle is Proxmox import-from (pulling the VMware disk). That is the usual bottleneck for ESXi and the IO path, so permits apply during the disk import, not for the whole migration.

  • Bucket — Permit pool key. For PVE volids sh12:ha-datacenter/…/disk.vmdk the bucket is sh12; for sh13:… it is sh13. Different buckets ⇒ parallel import-from up to worker.max_concurrent_imports_per_esxi_storage per bucket (typically 1).
  • Same bucket — Two jobs both using sh12:… share one pool ⇒ import-from is serialized for that storage id while others can still run on sh13.
  • Same VM — A second job for the same guest while one is still active is rejected at enqueue (409), stricter than the permit alone.
  • esxi:… paths — No storage-id: prefix; buckets use esxi:<datacenter>/<datastore-or-folder> (see repo doc). Short paths fall back to esxi_legacy_uri.
  • Optional merge — worker.esxi_import_permit_bucket_override maps several computed buckets onto one Redis pool (e.g. same ESXi host behind two PVE storages). Omit it by default so sh12 and sh13 stay independent and parallel.

Full detail: docs/import-permits-and-parallelism.md in this repository.

Potential roadmap (ideas, not commitments)

  • Preflight / dry-run — Validate enqueue inputs without starting destructive work.
  • Job metadata — Pool / wave labels for reporting; richer audit trail.
  • Live logs — SSE or WebSocket if log volume grows; split cheap vs deep health checks.
  • HTTPS-only cookies — Optional https_only when always behind TLS.

Security considerations

  • Exposure — Prefer private network or VPN; put the UI behind TLS (e.g. nginx). This tool drives Proxmox; treat it as admin-tier.
  • Secrets — config.yaml holds passwords and API tokens; restrict file permissions and backups. Redis holds job state and logs; use ACLs, auth, and a dedicated DB index; protect Redis dumps.
  • Sessions — Single shared dashboard password; session cookie flags depend on app settings — see SessionMiddleware in code. Consider login rate limiting at nginx for internet-facing installs.
  • Public endpoints — GET /health and GET /version need no login; they can reveal coarse dependency status — restrict by network if that matters.
  • Infrastructure accounts — Use least privilege Proxmox tokens and VMware roles; keep proxmox.safety aligned with what those accounts may touch.

Where things run

  • This web app — FastAPI UI + API (browser or reverse proxy).
  • Worker — Consumes Redis queue; talks to the Proxmox API (and optionally vCenter for inventory).
  • Redis — Job state, logs, queue (see deployment docs for host vs container Redis).
